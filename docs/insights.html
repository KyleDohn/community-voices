Where Things Go Wrong

Your sessions almost all succeeded, but the friction kept coming from three places: buggy first-pass code that reviews then had to catch, a fragile local Docker and tooling setup, and a few actions that ran without clear authorization, including one paid API call.

First-pass code needing review-driven fixes
Buggy code was your most common friction type. Test-first work and review subagents caught most of it before merge, but whole phases still shipped with real bugs that needed a fix-up round. You could ask Claude to run a self-review or mutation check before declaring a phase done, and include known pitfalls in each handoff (pgvector float formatting, Prettier line wrapping, macOS sed quirks) so the next session avoids them.
  • A review subagent found 13 bugs in the phase-4 code, which meant an extra fix cycle before you could close the phase.
  • Two test assertions were wrong at first (the concatenation collision case and pgvector float formatting), and a mutation substitution silently failed because Prettier had wrapped the target line.
Fragile local environment and Docker state
Several sessions lost time to environment problems rather than code: Docker not running, a full disk, stale dev-server modules, and CI billing locks. A short preflight checklist in your handoff template would catch most of these up front. It could cover Docker running, free disk space, a clean Vite cache, and GitHub billing status.
  • A full disk wedged Docker during phase 4, and recovery took several manual kill/restart rounds.
  • Your first public CI run failed because of a GitHub billing lock rather than a code problem, and Vite served a stale contract module that broke the page until a reload.
Unapproved or ambiguous actions
A few times Claude acted on its own reading of your intent: once with real cost, once on an ambiguous request, and once with destructive commands you denied. You could spell out hard rules in CLAUDE.md, such as 'never hit paid endpoints without explicit approval' and 'avoid rm -rf; use a fresh directory instead'. When a request could mean two things, phrasing it precisely ('start phase 3' vs. 'start Docker') also helps.
  • While verifying a rebuilt container, Claude sent an unapproved request that ran a real paid report ($0.055). It disclosed this itself, but the spend had already happened.
  • Claude read your 'can you start it' as starting Docker rather than beginning phase 3, and the session ended before the intent was clarified.

On the Horizon

Your phase-by-phase handoff workflow already turns Claude into a reliable multi-session builder, and the next step is letting it run whole phases on its own: parallel agents, review loops gated by tests, and safety rails that make running without supervision safe.

Autonomous phase execution with review loops
Your handoff document could become an executable spec. Claude would read it, break the work into tasks, implement each one test-first, run a review subagent, fix what the review finds, and repeat until format, lint, typecheck, unit and integration tests all pass. It would then write the next phase's handoff without you stepping in. Your review subagents found real bugs (13 in phase 4), so making the review-and-fix cycle automatic and repeated would catch those before you ever look at the code.
Getting started: Run Claude Code in headless mode (`claude -p`) with a custom slash command or Skill that holds the build, review and fix loop. Use the Task tool to start independent reviewer subagents with fresh context.
Paste into Claude Code:
Read HANDOFF.md and implement the entire phase autonomously. Process: (1) Break the handoff into a numbered task list and save it to docs/phase-plan.md. (2) For each task, write failing tests first, implement until green, run format/lint/typecheck/unit/integration, and commit with a descriptive message. (3) After all tasks, spawn 2 independent review subagents: one focused on correctness and edge cases, one on contracts/types and security. Have each produce a findings list. (4) Fix every finding with a regression test, then re-run the reviewers. Repeat until a review pass returns no high or medium findings, with a maximum of 3 rounds. (5) Run the full pre-submission red-flag check (secrets, debug markers, CI status). (6) Write the next phase's HANDOFF.md with interfaces, open risks and cost-guard notes. Never make network calls to paid APIs. Use mocks or recorded fixtures, and stop and ask if a real paid call seems required. Report a summary table of tasks, commits, review findings and their fixes at the end.
